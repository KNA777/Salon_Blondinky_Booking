# Отчёт по безопасности приложения Salon Booking

Дата: 2026-11-20. Версия кода: текущая ветка `main`.

Этот отчёт описывает модель угроз, уже реализованные меры защиты и рекомендации по
эксплуатации для защиты данных клиентов салона. Составлен для владельца продукта
(«покупателя»), без углубления в детали реализации.

---

## 1. Какие данные защищаем

Приложение хранит персональные данные клиентов и служебную информацию:

| Данные | Чувствительность |
| --- | --- |
| Имя и телефон клиента | Персональные данные (PII) |
| `telegram_id` клиента и мастера | Связывание с аккаунтом Telegram |
| Хеш пароля (bcrypt) | Аутентификация |
| Записи (кто, к какому мастеру, когда, какая услуга, цена) | Коммерческая + приватная информация |
| Токен бота Telegram, секрет webhook, ключ JWT | Критические секреты |

**Пароли никогда не хранятся в открытом виде** — только bcrypt-хеш. Поэтому даже если
база утечёт, злоумышленник не узнает пароли напрямую.

---

## 2. Что уже защищено (проверено в этой итерации)

### 2.1 Аутентификация и авторизация

- **Пароли** хешируются bcrypt (замедляющий алгоритм, устойчивый к перебору).
- **JWT access-токен** подписывается HMAC-SHA256 секретным ключом; проверяются подпись
  и срок жизни. Поддельный/просроченный токен отклоняется (401).
- **Токен передаётся в httpOnly cookie**: JavaScript на странице не может его прочитать,
  что защищает от кражи через XSS. Флаг `SameSite=Lax` ограничивает отправку куки на
  кросс-сайтовые запросы (основной вектор CSRF).
- **Владение записью**: клиент видит/меняет/отменяет/переносит только свою запись;
  чужая — HTTP 403. Администратор управляет любыми записями.

### 2.2 Исправленные уязвимости (этот раунд)

| Проблема | Было | Стало |
| --- | --- | --- |
| Утечка списка клиентов (имена + телефоны) | `GET /clients` был открыт всем | Только админ (403 остальным) |
| Просмотр чужого клиента по id | `GET /clients/{id}` открыт всем | Только владелец или админ |
| Изменение чужого клиента | `PATCH /clients/{id}` открыт всем | Только владелец или админ |
| Запись от чужого имени | `POST /appointments` позволял указать любой `client_id` | `client_id` обязан совпадать с текущим клиентом (или админ) |
| Просмотр чужих записей | `GET /appointments{...}` открыт всем | Клиент видит только свои; админ — все |
| Смена статуса без прав | `POST /appointments/{id}/status` открыт всем | Только админ |
| Изменение чужой записи | `PATCH /appointments/{id}` открыт всем | Только владелец или админ |
| Timing-атака на секрет webhook | сравнивалось через `==` | сравнение через `hmac.compare_digest` |

### 2.3 Защита входа через Telegram (Mini App)

`initData` из Telegram Mini App проверяется по официальному алгоритму HMAC-SHA256
(ключ `WebAppData` + `bot_token`). Подделанная подпись отклоняется (401). Без этой
проверки злоумышленник мог бы выдать себя за любого пользователя Telegram.

### 2.4 Защита от двойной записи

Двойной уровень: проверка конфликта на уровне приложения **и** exclusion-constraint в
PostgreSQL. Даже два одновременных запроса на один слот не создадут две записи.

### 2.5 Идемпотентность webhook

Повторный апдейт Telegram (с тем же `update_id`) обрабатывается один раз — защита от
двойного срабатывания бота при сбоях доставки.

### 2.6 Окружение prod (fail-fast)

Добавлена переменная `APP_ENV`. При `APP_ENV=prod` приложение **откажется стартовать**,
если:
- `JWT_SECRET_KEY` оставлен dev-дефолтом (иначе токены можно было бы подделать);
- `COOKIE_SECURE=false` (иначе access-токен ходил бы по открытому HTTP).

## 3. Что нужно знать владельцу (эксплуатация)

1. **Секреты не должны попадать в git.** Файлы `.env`, `.env.prod` — в `.gitignore`.
   Храните реальные значения только на сервере (или в защищённом менеджере секретов).

2. **JWT_SECRET_KEY** — длинная случайная строка (не менее 32 байт). Сгенерировать:
   `python -c "import secrets; print(secrets.token_urlsafe(48))"`.

3. **WEBHOOK_SECRET** — тоже длинная случайная строка, которую подставляете в
   `setWebhook` и в `.env`.

4. **HTTPS обязателен в проде.** Caddy в `docker-compose.prod.yml` даёт TLS
   автоматически (Let's Encrypt). Без HTTPS cookie с `Secure=true` не будет работать,
   а токен окажется уязвим к перехвату.

5. **БД и Redis не выставляйте наружу.** В `docker-compose.prod.yml` у них нет
   публичных портов — они видны только внутри сети Docker.

6. **Первый администратор** создаётся командой (не через публичный API, чтобы его
   не мог создать посторонний):
   ```
   docker compose -f docker-compose.prod.yml --env-file .env.prod exec api \
     python -m app.create_admin --name "Администратор" --phone "+7..." --password "..."
   ```

7. **Регулярно обновляйте зависимости** (`uv lock --refresh` + тесты), чтобы закрывать
   известные уязвимости библиотек.

## 4. Известные ограничения и рекомендации на будущее

Следующие меры **рекомендуются** для продакшена, но не блокируют базовый запуск:

- **Rate limiting** на `/auth/login` и `/auth/register` — защита от перебора паролей
  (сейчас нет лимитов на число попыток входа).
- **CSRF-токен** для state-changing эндпоинтов — частично закрыто `SameSite=Lax`, но
  для максимальной защиты стоит добавить явный CSRF-токен.
- **Секреты в менеджере секретов** (Vault/DO Secrets/1Password) вместо файлов на диске.
- **Аудит-лог** административных действий (кто и когда подтвердил/отменил запись).
- **Резервное копирование БД** (pg_dump по расписанию + проверка восстановления).
- **Мониторинг и алерты** (Prometheus/Grafana + Sentry) — сейчас логи по умолчанию.
- **Защита от массовой регистрации** (капча) на `/auth/register`, если эндпоинт
  доступен извне.
